## Full Architecture

### Layer 1 — Runtime Core

The heartbeat of everything is the **AgentLoop** ([loop.py](c:\Users\DELL\Documents\chinaza\builds\powerx-main (1)\powerx-main\nanobot\agent\loop.py)).

It runs a single `asyncio` event loop that:
1. Consumes inbound messages from a `MessageBus`
2. Acquires a per-session lock (serializes turns per session, concurrent across sessions)
3. Dispatches each message through a 6-stage pipeline:

```
RESTORE → COMPACT → COMMAND → BUILD → RUN → SAVE → RESPOND
```

- **RESTORE** — loads session, restores any interrupted turn checkpoint
- **COMPACT** — auto-compacts session history if token budget is near limit
- **COMMAND** — intercepts slash commands (`/stop`, `/new`, `/goal`, etc.)
- **BUILD** — resolves LLM runtime, builds prompt context (history + memory + skills)
- **RUN** — calls `AgentRunner._run_core()` — the actual LLM + tool loop
- **SAVE** — persists messages, clears checkpoint, triggers background consolidation
- **RESPOND** — assembles and publishes the outbound message

### Layer 2 — Agent Runner (Tool Loop)

`AgentRunner` ([runner.py](c:\Users\DELL\Documents\chinaza\builds\powerx-main (1)\powerx-main\nanobot\agent\runner.py)) is the pure LLM execution engine. It:

- Iterates up to `max_iterations` (default configurable)
- Each iteration: calls the LLM → if tool calls → executes tools concurrently (batched by `concurrency_safe`) → feeds results back → repeats
- Handles: streaming, length recovery (truncated outputs), empty response retries, malformed tool call recovery, SSRF/workspace violation classification, mid-turn message injection (subagent results), sustained goal continuation
- Emits durable **checkpoints** after every tool batch so a crash mid-turn can be recovered

### Layer 3 — Provider Abstraction

`nanobot/providers/` contains adapters for:
- OpenAI, Anthropic, Azure OpenAI, AWS Bedrock, xAI Grok, GitHub Copilot, OpenAI Codex
- A `FallbackProvider` that chains providers on failure

### Layer 5 — Trading Engine (`nanobot/trading/`)

This is the custom addition — a full ICT/SMC + HMM five-cluster strategy engine:

```
PollingEngine (real-time price watch)
        ↓
DataLoader → ScoutAgent (ICT/SMC features) + AnalystAgent (HMM regime)
        ↓
StrategyRouter → RouteDecision (Cluster A/B/C/D/E or skip)
        ↓
RiskManager (position sizing, daily loss lock, spread filter)
        ↓
AlpacaExecutionAdapter (submit order via alpaca-py)
```

- **ScoutAgent** — extracts ICT/SMC features from OHLCV bars using the `smartmoneyconcepts` package: FVG, Order Blocks, BoS, CHoCH, liquidity sweeps, displacement, killzone detection
- **AnalystAgent** — fits a 3-state `GaussianHMM` on log-returns to classify regime (Expansion / Retracement / Consolidation) and compute an AWD confidence score (45% HMM confidence + 35% TMA slope strength + 20% volatility ratio)
- **StrategyRouter** — maps the combined signal to one of 5 clusters (A=Institutional Reversal, B=Trend Expansion, C=Value Retracement, D=Correlation Basket, E=Range Liquidity) or skips if AWD < 0.65
- **RiskManager** — enforces 0.25% risk/trade, 5R daily loss lock, 3-pip max spread, sizes position by `risk_dollars / stop_distance`
- **PollingEngine** — async `WatchManager` that runs background price-watch loops, evaluates structured or NL conditions, auto-trades when triggered, persists run history to Supabase

## Key Design Patterns

- **Everything is async** — `asyncio` throughout, per-session locks prevent race conditions
- **Checkpoint-first persistence** — tool results are checkpointed before the next LLM call; crashes are recoverable
- **Skills as runtime context** — strategy knowledge is injected as prompt context, not hardcoded logic
- **Credential isolation** — per-user Alpaca keys in Supabase; env vars only as anonymous fallback
- **Graceful degradation** — `hmmlearn`, `smartmoneyconcepts`, Supabase all have `try/except ImportError` guards; the system runs without them

@app.post("/agent/run")
async def run_agent(body: AgentRunRequest):
    run_id = str(uuid.uuid4())
    # store pending run in Supabase, return run_id immediately
    asyncio.create_task(_execute_pipeline(run_id, body))
    return {"run_id": run_id}

@app.get("/agent/run/{run_id}/stream")

Each pipeline step emits an SSE event as it completes, giving the frontend its step-by-step animation.

## 5. Real-Time Strategy

**SSE over WebSocket** — rationale:
- Pipeline runs are one-directional (server → client)
- Next.js Route Handlers support `ReadableStream` natively — no extra infra
- SSE auto-reconnects; WebSocket requires manual reconnect logic
- Backtest can take 5–30 seconds — SSE keeps the connection alive with progress ticks

**Polling fallback** for account/positions: 5-second interval via `setInterval` + SWR. No need for WebSocket for account data.

**Kill switch** uses a regular `DELETE /api/positions` — no streaming needed, just a loading state.

Completed the full scan of the entire trading engine and tools codebase. There were **more than 30 findings** — because of the volume, you'll need to open the **Code Issues Panel** to see all of them with full details and suggested fixes.

Here's a summary of the critical categories I can confirm from reading the code directly:

---

**🔴 Critical / High**

- `alpaca_commands.py` — `/alpaca connect <api_key> <secret_key>` accepts credentials **inline in plaintext Telegram messages**. Those messages are logged by Telegram servers and potentially your own bot logs. There's no ephemeral handling.
- `alpaca_commands.py` — `_handle_status()` leaks partial API key in the response: `{creds['api_key'][:8]}...{creds['api_key'][-4:]}`. Even partial key exposure is a security smell for paper keys that could be reused.
- `alpaca_credentials.py` — `delete_credentials()` returns `True` unconditionally regardless of whether any row was actually deleted. A user who was never connected gets a success response.
- `polling_engine.py` — `_manager` is a module-level singleton. In multi-worker deployments (Render, Gunicorn), each worker has its own `_manager` — watches started in one worker are invisible to others. This is a silent correctness bug.
- `backtest_engine.py` — `position.stop = position.entry` mutates a frozen-ish dataclass field directly (it's a regular `@dataclass`, not `frozen=True`, so it works, but `breakeven_moved` is set on the object after the fact — the `position` object is shared by reference in the `positions` dict, which is fine, but the mutation pattern is fragile).

**🟠 Medium**

- `analyst_agent.py` — `directional_bias` logic is inverted: `tma_slope > 0` → `directional_bias = -1`. This is intentional for TMA mean-reversion (positive slope = price above TMA = expect short), but it's undocumented and will confuse anyone reading the code. The comment in SKILL.md explains it, but the code itself has no inline note.
- `trading_commands.py` — `_backtest_text()` ignores the `timeframe` argument passed from `handle_backtest_command()`. The config is always `AgentConfig()` with `timeframe="1h"` regardless of what the user requested.
- `strategy_router.py` — Cluster A checks `scout.choch_direction` as a truthy int, but `choch_direction=0` is falsy. If CHoCH direction is 0 (no signal), the condition silently fails rather than explicitly rejecting. Same pattern in Cluster B with `scout.bos_direction`.
- `alpaca_adapter.py` — `get_bars()` silently drops the symbol level from a MultiIndex without validating it's the right symbol. If `symbol_or_symbols` returns multi-symbol data, the wrong symbol's bars could be returned.

**🟡 Low / Quality**

- `data_loader.py` — `load_market_data()` collects all failures then raises a single combined error, but the partial `data` dict is discarded. Callers get no partial results even when only one of six pairs fails.
- `tma_engine.py` — `nb_tma()` returns `None` if any single weight is non-finite, making the entire slope `None`. A single bad candle in a 500-bar window kills the signal for that bar.

## 3. Real-Time Update Strategy

**Chosen approach: Server-Sent Events (SSE) for the console pipeline only. Polling for everything else.**

Rationale:
- The existing API already uses REST + React Query polling (30s refetch). This works fine for dashboard, activity, account.
- The console pipeline needs step-by-step streaming. SSE is the right fit: unidirectional, no WebSocket overhead, works through proxies, native browser support.
- No new WebSocket infrastructure needed.

**SSE endpoint:** `GET /api/agent/console/stream?symbol=SPY&strategyMode=zscore&idempotencyKey=<uuid>`

The server runs the full pipeline sequentially, emitting one `data:` event per step as each completes. The client uses the native `EventSource` API (or a thin wrapper) to consume events and drive the stepper UI state machine.

**Idempotency:** The client generates a `crypto.randomUUID()` before each console run and passes it as a query param. The server stores it on the order submission call and rejects duplicate keys within a 60-second window.
